# Final amplifier: DCA4 + saturation + pan (`Camp`, unit `mod_amp4_13`)

C++: `src/engine/Amp.{h,cpp}` (`sq8l::Amp`, `sq8l::ampTables()`), data
`src/engine/data/AmpData.cpp` (generated by `re/scripts/extract_amp_data.py`).
Test: `tests/test_amp.py` + `tests/capi_amp.cpp`. Status: **bit-exact** on every captured call
(see "Verification").

One `Camp` per voice slot (16, master voice slot `+0x7c`). It takes the filtered voice sample
(x87 ST0, from `CfilterSQ.process`), optionally saturates it, multiplies it by a left and a
right gain and **adds** the result to the stereo accumulator `float[2]` of the current sample.
The two gains are `pan law × DCA4 level curve × gain`; every control tick (83.59 Hz) new target
gains are set and reached by a linear ramp (DCA4 smoothing EMU/HARD = ramp time).

The unit init procedures run in DllMain with the host's FPU control word (round to nearest,
53 bits); `ampTables()` builds them lazily under `RoundToNearest`.

Unit init plumbing: mod_amp4_13 init = 0x45eac0 (counter 0x4c560c), satTables init = 0x45e43c
(counter 0x4c5608); the finalizers (0x45ea90, 0x45e40c) do nothing else.

## How plugCore drives it

* **Master constructor** `FUN_00461cac` (0x461e37): `slot.amp = Camp.Create(sampleRate)` for
  the 16 voice slots (`init()`). Destructor: `FreeAndNil(slot.amp)`.
* **Sample rate** `FUN_00462214` (only when the rate changes and is >= 40000):
  `amp.setSampleRate(Single(rate))` for every slot (round to nearest). It also runs once inside
  the master constructor.
* **Voice start** `FUN_004625d4` (inside processReplacing → round toward zero):
  `amp.setSaturation(prog[0x13a])`; when the voice is (re)started (arg `[ebp+8]` true):
  `amp.start(takeover ? &voice[+0x28].amp : nullptr)` — takeover (`[ebp-0x1d]`) is the
  voice-restart case: the same key is struck again while its previous voice still sounds and
  the program's restart flag `prog[0x22+0x152]` is set (56 of the 168 bank C/D programs), so
  the new voice continues the old one's gains; then
  `voice[+0x80] = mode` (global override `master+0xff0` > 0 → `(ff0-1)&1`, else
  `(prog[0x196] >> 1) & 1`; 0 = EMU, 1 = HARD) and
  `amp.setRampTime(rampTimes[mode][min(prog[0x22+0x79], 3)])` (env 4 T1).
* **Control tick** `FUN_00463890` (every `master+0xf80`/1024 samples, RZ):
  `amp.setSaturation(SAT)`, `amp.setSmoothing(smoothTable[mode])`,
  `amp.setLevelPan(level, pan, filter0.level /* CfilterSQ +0x14 */, false)` where level comes
  from final volume, velocity, env 4, controllers and the final-volume modulator (it can leave
  0..255; the amp clamps), pan = `prog[0x133]` + `voice[+0xdc]` (from the note record) +
  (pan modulation + modulation source 0x18 - 64) / 128 (can leave ±63; the amp clamps). The
  amp is never updated with `immediate` here. When `voice[+0xe0] == 1` (it is reset to 0 at
  voice start and incremented after each tick, i.e. on the second tick of a note)
  `amp.setRampTime(rampTimes[mode][3])` (10 ms) replaces the attack ramp time.
* **Per sample** `FUN_00464410`: `x = filter.process(doc.render())`, then
  `voice[+0x30] == 0 ? amp.process(x, out) : amp.processFade(x, out, voice[+0x3c])`; plugCore
  then advances its own fade gain (`+0x3c += +0x40` while `+0x38` counts down).
* **Voice end**: when env 4 has finished (`[voice+0x70]+0x60 == 0`) the voice is still rendered
  while `amp.rampCount > -doc[+0x209c]`, then released. **This is the only field plugCore reads
  directly** (`Amp::rampCount`, public).

plugCore-owned tables used for the amp (unit transTables, not part of this port):
`rampTimes` = `[0x4c33fc]` → 0x4c2530: EMU {0.0025, 0.004, 0.005, 0.01} s,
HARD {0.0006, 0.0014, 0.004, 0.01} s; `smoothTable` = `[0x4c32f0]` → 0x4c2550: {0, 0}
(so level smoothing is never enabled in 0.91b).

Shared state: only the read-only tables. `start(from)` reads another voice's `Amp`.

## Quirks (kept for bit-exactness)

* `start(from)` copies `from->stepR` into `stepL` (the original reads +0x10 twice).
* A ramp applies `rampLength + 1` steps (one in `setLevelPan`, one per sample while
  `rampCount > 0`), overshooting the target by one step; the next control tick snaps `vol` to
  the previous target if the ramp has ended (`rampCount < 0`).
* `rampStep = 0` when `0 < t·sr < 1` (rampLength 0): the gains then do not move until the
  next tick snaps them.
* Targets never go below 1e-6 (≈ -120 dB): a "silent" voice is never exactly 0.
* SAT off (`satIndex = -1`) uses gain 0.584 without saturation; SAT = 0 already saturates
  (drive 0.73, gain 1.0). SAT ≥ 16 → index 63 (drive 12, gain 0.58). Factory programs use
  SAT 0..4 and 9.
* Clip of NaN gives -1 (FTST sets C0 for unordered).
* `rampCount` keeps decrementing forever and wraps to +2^31-1 after ~13.5 h of continuous
  rendering at 44.1 kHz (only matters for a voice held that long).
* Level smoothing (`setSmoothing` > 0) is dead code in 0.91b (plugCore always passes 0).
* `setSaturation` computes `4·sat + 1` in 32 bits; plugCore passes a signed byte (sat ≥ 2^29
  would make the original read outside the table).

## Verification (`tests/test_amp.py`)

* Tables: pan law (254 Singles), both saturation tables (260 Singles) and the DCA4 curve
  (256) equal the emulator memory after load and after playing; the table pointers still point
  to them.
* Every call of every routine made while the emulated plugin plays programs of banks C and D
  (chord with varied velocities, a repeated key, staggered note-offs), voice stealing (12
  overlapping notes on 6 programs → `processFade`), edit-buffer tweaks (SAT -128/-1/15/16/127,
  pan and final-volume modulation driving pan and level out of range) and a sample-rate change
  44100 → 48000 → 44100 is replayed on the C++ object loaded from the captured bytes:
  outputs, FPU stack effect and all object bytes must be identical. Calls happen under the
  control word of the call (RZ in process, RN at load/SR change).
* Paths the plugin never takes (level smoothing, ramp times giving length 0 or overflowing
  Round, saturation values outside the factory range, extreme samples, NaN/inf gains) are
  checked by direct calls of the original routines (`emu.call_fpu`).

Known deviations: none on reachable inputs. On non-finite inputs (inf/NaN `gain` argument,
never produced by plugCore) the C++ produces NaN where the original does, but the NaN encoding
can differ (x87 default NaN is 0xffc00000, the host's may be 0x7fc00000).
The x87 registers keep a 15-bit exponent even at 53-bit precision, so a product that
underflows in IEEE double (e.g. `x²` for |x| < 2^-511, `x·vol` for |x·vol| < 2^-1074) stays
nonzero on the original; under round-toward-zero such a tiny negative term can move a sum by
one ulp. Samples that small never reach the amp: they are filter outputs built from Single
stages and coefficients (every captured ST0 was checked to be a normal double), and
`tests/test_amp.py` found no difference on any real or synthetic input (1e-130 included).
